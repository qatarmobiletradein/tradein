# API

Base path `/v1`. JSON in, JSON out. Every response carries `X-Request-Id`. Errors are `{ ok:false, message, code }` with a human sentence — never a stack trace or a constraint name. Generated from the live registry (`apps/api/src/registry.ts`, `registry-more.ts`, `routes/rest.ts`).

## Conventions
| Header | Meaning |
|---|---|
| `Authorization: Bearer <access token>` | Supabase access token. Required for everything except health, public and auth start/verify/register/refresh. |
| `Idempotency-Key` | `^[A-Za-z0-9_-]{16,128}$`. For actions marked *idem*: a retry with the same key returns the **original** result (plus `"replayed": true`); the same key with a different payload → `409`. **Required in staging and production** (missing → `428`); optional only in development/test. May also be sent as `params.idempotencyKey`. |
| `X-Request-Id` | Optional; kept only if well-formed, otherwise replaced. |

Status codes: 200 ok · 400 invalid input · 401 no/expired/revoked session (`reauth:true`) · 403 forbidden · 404 not found (also used for out-of-scope objects so ids cannot be probed) · 409 conflict (duplicate, invalid transition, idempotency mismatch) · 413 too large · **428 `IDEMPOTENCY_KEY_REQUIRED`** (staging/production: an idempotent action sent without a key) · 429 rate limited · 503 unavailable · 500 generic.

Machine-readable description: **`docs/openapi.json`** (OpenAPI 3.1, generated by `npm run openapi`, validated and drift-checked by the tests). Management summary: `API_HANDOFF.md`.

## Compatibility endpoint
`POST /v1/actions/:action` with body `{ "params": { ... } }` — the same action names the 3.1 frontend sends through `google.script.run.apiCall`. Unknown and forbidden actions return the same response. Sign-in actions (`auth.start/verify/register/refresh/logout/logoutAll`) are **not** served here — only under `/v1/auth/*`, which has the stricter rate limit (the shim already routes them there).

Notes
- `* = any signed-in principal` still applies scope (e.g. a customer's notifications only).
- `admin.advanceSettlement` to `APPROVED` additionally requires SUPER_ADMIN (`requireSettlementApprover`), as 3.1.
- `admin.saveSetting` is SUPER_ADMIN only.
- `cancelTradeIn` exists in the service layer but, as in 3.1, is **not** exposed as an action.
- I'm not certain every 3.1 response field is reproduced byte-for-byte; the browser smoke test signs in three roles and renders their portals, but not every screen was clicked through (see `TEST_RESULTS.md`).
